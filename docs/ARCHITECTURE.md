# Архитектура

## Общая схема конвейера (целевая)

```
PDF ─► [1. Извлечение] ─► [2. Сверка с чертежами] ─► [3. Подбор по базе] ─► [4. Цены] ─► [5. Excel/КП]
          PyMuPDF/OCR         геометрия планов          1С + LLM             1С + веб       openpyxl
```

Каждый шаг — отдельный модуль с явным входом и выходом (pydantic-модели из
`core/app/models.py`). Шаг можно перезапустить отдельно, а его результат — посмотреть
и поправить руками до следующего шага. Этап 1 реализует шаги 1 и 5.

## Три части

```
web (React) ──► api (ASP.NET Core) ──► core (Python)
```

- **core** — ядро разбора. Внутренний HTTP-сервис без авторизации, CORS и статики: наружу
  его не публикуют. Всё, что связано с PDF, OCR и Excel, живёт здесь.
- **api** — обвязка на C# по Clean Architecture (`Domain → Application → Infrastructure → Api`).
  Единственный вход для фронта. Ядро подключено через порты `IParsingEngine`
  (`Application/Parsing`) и `IPricingEngine` (`Application/Pricing`), реализации —
  `PythonEngineClient` и `PythonPricingClient` в Infrastructure: заменить ядро (другой
  процесс, in-process) — сменить одну регистрацию. Сюда встанут следующие этапы: хранение
  проектов, 1С онлайн, интернет-цены.
- **web** — интерфейс, в разработке проксирует `/api` в api. Рабочее пространство объекта
  (`src/store.ts`, zustand + localStorage): список загруженных томов и правки менеджера к
  своду. Правки хранятся прямо в объектах строк; строка свода на клиенте — `SummaryRow`
  (= `SummaryItem` + пометка `excluded`). Выгрузка (`src/export.ts`) собирает из томов один
  `ParsedDocument`: строки склеиваются, исключённые убираются, `documents` перечисляет
  исходные PDF — ядро строит по нему общий Excel. Ядро и api про рабочее пространство не
  знают; когда появится хранение проектов на сервере, оно ляжет в api.

Контракт JSON везде snake_case: типы фронта (`web/src/api.ts`), доменные записи C#
(`DomeoSpec.Domain/Specifications`) и pydantic-модели ядра описывают одну и ту же структуру.

Ошибки в api: `ValidationFailedException` → 400, `EngineFailureException` (ядро не смогло
разобрать) → 422, `ServiceUnavailableException` (ядро не отвечает) → 503 + `Retry-After`;
всё как ProblemDetails с полем `code`.

## Ядро: разбор PDF

```
core/app/
  parsing/
    pdf_reader.py   слова с координатами + линии таблицы (PyMuPDF), фильтр штампов
    ocr.py          сканы: растр → слова (Tesseract) + линии таблицы с растра (numpy)
    geometry.py     Word, Rules, PageData; группировка слов в строки
    table.py        шапка → столбцы → строки → ячейки (независимо от проектировщика)
    spec_parser.py  документ целиком: страницы → позиции, группы, метаданные
    aggregate.py    свод одинаковых позиций по документу
  export/excel.py   три листа Excel по образцу приложения к договору
  main.py           FastAPI: /api/parse, /api/export, /api/health
  cli.py            то же из командной строки
```

### Ключевые решения

**Координаты, а не текст.** Текстовый поток PDF перемешан (штамп, повёрнутые подписи,
многострочные ячейки), поэтому разбор идёт по геометрии: каждое слово имеет bbox,
ячейка — это пересечение полосы строки и полосы столбца.

**Поворот страниц.** Листы спецификаций часто хранятся с `/Rotate 90`. PyMuPDF отдаёт
координаты в неповёрнутой системе; всё умножается на `page.rotation_matrix`, и дальше
таблица всегда «стоячая».

**Границы столбцов и строк — из линий таблицы.** Проектировщики рисуют рамки по-разному
(одна длинная линия или отдельная рамка у каждой ячейки), поэтому `Rules` копит
*суммарную длину* отрезков на каждой координате; настоящая граница набирает ≥35 %
высоты/ширины таблицы, случайный штрих — нет. Если линий нет (плохой скан), столбцы
берутся по ячейкам шапки, строки — по якорным ячейкам (позиция/ед./кол-во стоят по
центру строки).

**Шапка узнаётся по словам.** Столбец получает роль по началу слова в шапке:
«Поз»→`pos`, «Наименование»→`name`, «Кол»→`qty` и т. д. Таблица считается спецификацией,
если найдены хотя бы `pos`, `name`, `qty`. Это позволяет не привязываться к
конкретной форме.

**Штампы.** Блоки текста «В производство работ», «Передан через Диадок», UUID документа
выбрасываются целиком; блоки в их окрестности (организация, ФИО, дата) — по шаблонам.
Основная надпись листа (штамп внизу) ограничивает таблицу снизу: ищутся слова
«Изм.», «Лист», «Подп.» внутри ширины таблицы (на полях слева стоят такие же слова,
их учитывать нельзя).

**Группы.** Строка без единицы и количества — заголовок группы: помещение
(«1.01 Групповая комната…») или раздел («ПИЩЕБЛОК»). Группа действует до следующего
заголовка, в том числе через границу страницы. Первая строка страницы без позиции,
начинающаяся со строчной буквы, — продолжение описания с прошлой страницы.

**Свод.** Ключ свода — нормализованная позиция + нормализованное описание. Одна позиция
с разными описаниями попадает в две строки и получает замечание (так в PDF ловятся
опечатки проектировщика).

**Сканы.** Отсутствие текстового слоя → растр 300 dpi → линии таблицы ищутся на растре по
длинным прогонам тёмных пикселей → по сетке линий вырезаются непустые ячейки, складываются
столбиком в один холст и распознаются **одним вызовом OCR на страницу**; слова возвращаются
на свои места по таблице смещений и пересчитываются в пункты. Так сделано потому, что
Tesseract по целой странице теряет шапку таблицы (короткие ячейки между линиями он
выбрасывает как «не текст»), а по ячейкам читает всё. Без сетки — распознаётся страница
целиком. Дальше тот же `table.py`. Провайдер OCR — протокол `OcrProvider`; сейчас Tesseract
(в образе ядра стоит с русским пакетом), можно подключить облачный без изменения конвейера.
Проверено на синтетическом скане настоящим Tesseract (тест `test_scan_with_real_tesseract`,
локально пропускается без бинарника).

**Замечания вместо тишины.** Всё, что разобралось неуверенно (нет количества, странная
позиция, продолжение описания, страница без OCR), пишется в `warnings` строки, страницы
или документа и попадает в лист «Проверка». Менеджер смотрит только на жёлтые строки.

## Модель данных

- `SpecItem` — строка как в PDF: позиция, описание, тип/марка, изготовитель, ед., кол-во,
  примечание, группа (помещение), страница, замечания.
- `SummaryItem` — сведённая позиция: общее количество, список помещений с количеством,
  раздел для КП, базовая цена за единицу (`price`) и её источник (`price_source`: вручную /
  мин, макс, медиана, последняя по истории / интернет), результат сопоставления с историей
  закупок (`history: HistoryPrice` — вид совпадения, лучший кандидат, кандидаты, покупки;
  у кандидата `alias` — название у поставщика, если совпало по нему, а не по нашему),
  зарезервированная цена из интернета (`internet_price/source/date`), шифр
  документа-источника (`source_doc`).
- `SourceDocument` — сводка по исходному PDF (шифр, файл, страницы со спецификацией/OCR/
  пропущенные, строк, позиций, замечания). После разбора — один элемент в
  `ParsedDocument.documents`; в выгрузке из нескольких томов — по одному на том.
- `ParsedDocument` — файл, шифр, объект, страницы (вид/источник/замечания), строки, свод,
  исходные документы.
- `ExportRequest` — то же, что `ParsedDocument`: фронт может прислать отредактированные
  данные (в том числе объединённые из нескольких томов), и Excel соберётся из них. Поле
  `kind` выбирает книгу: `kp` — приложения к договору, `cost` — себестоимость, `working` —
  рабочая выгрузка (без `kind` — `kp`, если передан `kp`, иначе `working`).
- `PriceListInfo` — сводка по прайсу закупки (файл-источник, когда собран, строк в
  выгрузке, позиций, покупок, выбросов, период). `MatchRequest/MatchResponse` — позиции
  на сопоставление (`id`, `name`, `description`) → `{ id: HistoryPrice }`.

## Excel

Образец заказчика («Приложение 1.xlsx») — книга из двух листов: «1» — Приложение №1.1
«Спецификация на Товар/Оборудование, подлежащего монтажу/пусконаладке» (графы A–O с
СМР: `H=J/(1+L)`, `I=H*F`, `J=M-K`, `N=F*M`, итог «Итого с НДС» `SUM(N)`), «2» —
Приложение №1.2 «Спецификация на Товар (инвентарь), не подлежащего монтажу» (графы A–M
без СМР: `H=K/(1+J)`, `I=H*F`, `L=F*K`, итог «Всего с НДС» `SUM(L)`). На обоих —
автофильтр на шапке, группировка строк, за областью печати графы-подсказки «пр / дост /
монт» и ссылка на итог, внизу блок подписей: «Заказчик:/Поставщик:», должность жирным,
дальше только линии. Нумерация «№» сквозная по обоим листам, как в образце.

## КП

**Формирование КП = эта книга с ценами.** `SummaryItem.price` — базовая цена за единицу с
НДС (закупочная, найденная или введённая вручную), `SummaryItem.installation` — подлежит ли
позиция монтажу (лист «1») или это инвентарь (лист «2»). Правила (`KpSettings`,
`core/app/export/kp.py`, зеркало — `web/src/kp.ts`):

```
цена в КП  = база × (1 + наценка) × (1 + доставка)  → «Цена за ед. товара, с НДС»
СМР за ед. = цена в КП × СМР %  (только лист «1»)   → «Цена за ед. СМР, с НДС»
M          = цена в КП + СМР                        → «Цена за ед. товара (вкл. СМР), с НДС»
без НДС    = цена в КП / (1 + ставка НДС)           → формулой в Excel
```

Доставка входит в цену товара (в образце это графа-подсказка «дост» у строки), отдельной
строки нет. Параметры: договор № и дата (шапка «Приложение №… к Договору № … от …»),
должности подписантов, НДС, наценка, доставка, СМР, округление. Позиции без базовой цены
остаются в приложениях с пустыми ценовыми графами.

С `kind: kp` ядро отдаёт только листы «1» и «2» (файл для заказчика); `working` —
рабочую выгрузку: «Спецификация» (форма 1.1, база в M как есть), «По помещениям»,
«Проверка». Параметры КП живут в рабочем пространстве фронта (правила и должности
переживают смену объекта); api пропускает их в ядро как часть `ParsedDocument.Kp`.

## Себестоимость: цены из истории закупок

Заказчик считает не КП, а сначала **себестоимость**: у каждой позиции три цены — интернет
на дату, минимум и максимум по истории закупок, оператор выбирает одну, из неё уже
считается КП. Реализованы все три источника: история закупок, каталоги поставщиков
(бесплатно, по решению заказчика — «нужна проверка цен на рынке») и веб-поиск моделью
(платно). Второй и третий подставляются в одну графу «Интернет на дату» через общий порт
`PriceSearchProvider`, выбор — переменной `PRICE_SEARCH_PROVIDER`.

**Прайс закупки** (`core/app/pricing/`). Источник — выгрузка 1С «Заказы поставщикам»
(xlsx, ~28 тыс. строк за несколько лет): номенклатура, текстовое описание, группа
аналитического учёта, заказ на сборку / количество собрать, комплектующая, документ
заказа (с датой), номенклатура партнёра, количество, сумма. `history.py` читает её
(read-only openpyxl) и нормализует наименования (регистр, ё, знаки препинания;
токены ≥3 символов без стоп-слов). `pricelist.py` собирает `PriceList`: одна запись на
нормализованное наименование, по ней — список покупок (дата, цена за единицу = сумма /
количество, количество, номенклатура партнёра, заказ). Наборы (строки с заказом на
сборку) сводятся к цене комплекта: сумма комплектующих / количество собрать, одна
покупка «комплект: N компонентов». Выбросы (цена в 5+ раз выше или ниже медианы по
позиции) помечаются и в эталоны (мин / медиана / макс / последняя с датой) не входят,
но в списке покупок остаются серым. Прайс хранится как `pricelist.json` в `DATA_DIR`
(`PriceListStore`, один прайс на сервис; в контейнере — том `/data`, переживает
пересборку образа) и подхватывается при старте ядра.

**Сопоставление** (`matching.py`). Индекс по токенам прайса; для позиции спецификации
берутся токены наименования. Токен — основа значимого слова (`history.analyze_name`,
`synonyms.py`): русский стеммер Snowball (`snowballstemmer`), беглая гласная
(котел/котла), словарь сокращений и уменьшительных (нерж → нержавеющий, столик → стол,
навесной → настенный), составные «электро…» (электроплита = плита электрическая) и обороты
(ванна моечная = мойка, СВЧ = печь микроволновая, ПММ = машина посудомоечная); склейки
стеммера, путающие разные слова, поправлены (белья ≠ белый). Словарь короткий намеренно:
пословно из истории синонимы не учатся — там «видеокамера» путается с «камерой
холодильной». Балл = 0.65·доля токенов позиции, найденных у кандидата, + 0.35·доля
токенов кандидата, найденных в позиции, +0.15 за общий префикс наименования в 20
символов. Если у позиции и кандидата разные главные слова (первое существительное: «Стул
для обеденного стола» и «Обеденный стол с 4 стульями»), кандидат — не выше аналога. При
равном балле вперёд позиция с большим числом закупок. Кроме нашего наименования,
позиция находится по **номенклатуре поставщика** из истории (до 5 названий на позицию,
пометки учёта «(Астра)», «*» срезаются; без бонуса за префикс, нужно ≥ 2 общих слова,
балл не выше 0.95) — кандидат тогда несёт `alias`. Виды: `exact` — нормализованные
наименования совпали; `fuzzy` — балл ≥ 0.6; `analog` — балл ≥ 0.3 (в интерфейсе и Excel
помечен, оператор проверяет сам); `none`. К результату прикладываются до 5 кандидатов и
до 10 последних покупок лучшего — чтобы оператор видел, откуда цена. `market_names` отдаёт
для поиска цен до двух названий у поставщиков при уверенном совпадении: не общее нашего
(«Шкаф-сушка» при «Шкаф-сушка настенный» не берётся, с номером модели — берётся) и не
чужое (другое главное слово без общих слов — скорее деталь или замена). Подбор аналога по
характеристикам через модель — отдельный шаг, см. `docs/PLAN.md`.

**Цена из интернета** (`core/app/pricing/internet.py`). Провайдер поиска — за протоколом
`PriceSearchProvider`; реализация `ClaudeWebSearchProvider`: один запрос к Claude API
(`claude-opus-5` по умолчанию, effort `medium`) с серверным инструментом
`web_search_20260209` (до 4 поисков, локация RU/Москва) — модель сама ищет, читает
страницы и отвечает JSON: до 6 предложений (название, ссылка, продавец, цена за единицу с
НДС, пометка «аналог», примечание), рекомендуемая цена (типичная среди подходящих, не
самая низкая) и комментарий. Ответ разбирается терпимо (`extract_json`, `parse_lookup`:
ограждения ```json, цены строкой «1 200,50 ₽», медиана вместо отсутствующей цены). Отказ
модели или нечитаемый ответ — статус `error` с текстом, не исключение; на отказ по политике
запрос сам уходит на запасную модель (`fallbacks: "default"`). `InternetPriceService`
держит кэш `DATA_DIR/internet_prices.json` (ключ — нормализованные наименование и
характеристики; свежее `ttl_days` = 7 не ищется заново, у результата есть своя дата),
одинаковые позиции в пачке ищет один раз, ошибки не кэширует, работает пулом на 3 потока.
Без ключа `ANTHROPIC_API_KEY` провайдера нет: `GET /api/internet` отвечает
`configured: false`, `POST /api/internet/lookup` — 409. Ключ ядро берёт из окружения или
из `core/.env` (`app/env.py`, локальный запуск); на стенде — `deploy/secrets.env`.

Фронт шлёт позиции пачками по 8 (`POST /api/specifications/internet/lookup`, до 50 за
запрос — поиск занимает десятки секунд на позицию), показывает прогресс и даёт остановить;
результат ложится в строку (`internet`), рекомендуемая цена и ссылка выбранного предложения —
в `internet_price/source/date`; в раскрытии видны все предложения, щелчок по любому делает
его ценой из интернета, а если базовая цена уже взята из интернета — она следует за выбором.
Ошибка поиска не стирает прежний удачный результат. Число поисковых запросов (`searches`)
возвращается для оценки расходов.

**Слои.** Порт `IPricingEngine` в Application (загрузить выгрузку → `PriceListInfo`,
сводка, сопоставить), реализация `PythonPricingClient` в Infrastructure (HTTP к ядру:
`/api/pricelist`, `/api/pricelist/match`; 404 → `null`, 409 «прайс не загружен» →
`validation_failed`), контроллер `api/specifications/pricelist`. Фронт: вкладка
«Себестоимость» (`CostPanel`) — статус прайса и загрузка выгрузки, кнопка «Сопоставить
с историей» (порциями по 500 позиций), таблица с графами интернет / мин / макс /
последняя и выбранной ценой; щелчок по цене или массовое «везде …» записывает `price`
и `price_source` в строку свода, так что КП считается от выбранной цены без лишних
действий. Результат сопоставления лежит в строке (`history`) и переживает перезагрузку
вместе с рабочим пространством.

**Каталоги поставщиков** (`core/app/pricing/suppliers/`). `extract.py` вытаскивает
предложения из HTML в порядке надёжности: schema.org JSON-LD (Product → Offer /
AggregateOffer, только рубли), микроразметка itemprop, OpenGraph `product:price:amount`,
эвристика «единственный h1 + первая цена»; плюс разбор фидов YML и карт сайта (индексы,
gzip). `crawler.py` (`SiteCrawler`) идёт от дешёвого к дорогому: фид YML по типовым
адресам → карта сайта из robots.txt и `sitemap.xml` (карточки товаров вперёд, служебные
разделы мимо) → переходы по ссылкам; robots.txt уважается, пауза 0,5 с между запросами,
лимит страниц, колбэки прогресса и остановки, клиент httpx подменяется в тестах
(`MockTransport`). `xlsx_import.py` читает прайс-лист: ищет шапку со словами
«наименование» и «цена» (предпочитая «с НДС»/«розн.»), иначе угадывает колонки по
содержимому. `index.py` (`SupplierIndex`) хранит поставщиков и их предложения в
`DATA_DIR/suppliers/`, запускает обход отдельным потоком на поставщика (статус, прогресс,
остановка; прерванный перезапуском обход помечается ошибкой), а поиск делает
`OfferMatcher` — тот же индекс слов и та же оценка, что у сопоставления с историей:
≥ 0.6 — совпадение, 0.45–0.6 — похожее (помечается как аналог), до 6 предложений,
рекомендуемая цена — медиана по совпавшим, в комментарии разброс и число поставщиков.
В совпадение не попадает «соседний» товар с теми же словами: нужно ≥ 2 общих слова (если
в запросе их два и больше), первое слово запроса — в предложении, главное слово
предложения — в запросе, и предложение не во множественном числе там, где в проекте
единственное («Стулья с пюпитром» у магазина — страница раздела с ценой «от»). Такие
остаются «похожими». В сопоставление не идут цены-заглушки (1 ₽) и SEO-заголовки разделов
(«… в Хабаровске», «купить», «оптом», «Главная» — `extract.looks_like_listing`, их отсеивает
уже извлечение); хвост заголовка страницы («Наушники - Учебные материалы | …») срезается
(`product_name`). Если по нашему названию магазинов меньше `min_shops`, поиск добавляет
**названия из истории закупок** (`market_names`): такое совпадение помечено «по названию из
истории закупок «…»» и засчитывается, только если у предложения есть общее слово с нашим
названием или оно начинается с марки.
Поверх слов — **параметры** (`pricing/params.py`): из характеристик позиции и из названия
предложения вытаскиваются габариты (2000х1000х400(h), 2,0×1,0×0,4 м, 120х60 см, варианты
высоты 460/520/580), объём в литрах, масса, мощность, диаметр и счётные признаки (число
секций, конфорок, створок, дверей, ярусов, уровней, полок, гнёзд, мест: «двухсекционная»,
«4-х конфорочная», «4 полки»); всё приводится к мм / л / кг / кВт, сравнивается с допуском
5 % и без учёта порядка осей. Противоречие опускает оценку ниже порога совпадения (в цену
не входит, пометка «параметры не совпали»), подтверждение добавляет 0.1 («параметры
совпали»; если часть параметров у продавца не указана — «параметры совпали не все»),
отсутствие параметров у предложения оставляет оценку как есть («параметры не указаны», в
комментарии — просьба проверить размер). Габариты и прочие меры (без счётных признаков —
они и так в названии) уходят в запрос к поисковику; если по запросу с параметрами цен нет,
поиск повторяется без них.
`SupplierIndexProvider` подставляет это в `InternetPriceService` (кэш не используется —
индекс локальный).

**Автопоиск** (`pricing/websearch.py`, `suppliers/discovery.py`, `AutoSearchProvider`).
Поисковик за протоколом `SearchEngine`: `DdgsEngine` (библиотека ddgs — DuckDuckGo, Bing,
Яндекс и другие без ключей, режим `auto` перебирает источники) или `SearxngEngine`; общий
троттлинг — один запрос в полторы секунды на сервис. `WebPriceSearch.find` по позиции
строит запрос «наименование купить», отсеивает маркетплейсы и не-магазины, читает до 8
страниц (не больше двух с сайта, robots.txt), вытаскивает предложения тем же `extract`,
кэширует результат по запросу на 7 дней и отдаёт найденное в `SupplierIndex.discover`:
магазин заводится как поставщик с пометкой `discovered` и запросом, его предложения
добавляются в индекс (`append_offers`, матчер пополняется без пересборки), а сайт встаёт в
очередь на обход каталога — один фоновый поток обходит очередь по одному сайту с
глубиной `autocrawl_pages` (настройка индекса; 0 — выключено). Обход по кнопке идёт
своим потоком, вне очереди. `AutoSearchProvider.lookup`: сначала индекс (`rank` → `build_lookup`); если
разных магазинов с той же позицией меньше `min_shops` (настройка индекса, по умолчанию
3) — автопоиск, затем снова индекс (он уже пополнен); если магазинов всё ещё мало, а в
истории закупок у позиции есть название у поставщика (`market_names`, передаётся из
`PriceListStore`), ищется и оно — у поставщика это обычно конкретная модель («Кипятильник
Фонтан АКНЭ-100» вместо «Кипятильник электрический»). Повтор той же позиции в течение
недели берёт страницы из кэша поиска, поисковик не трогается. Сбой поисковика или
пустая выдача не роняют пачку: возвращается ответ индекса с пометкой в комментарии.
Фронт при открытии вкладки «Себестоимость» сам запускает сопоставление с историей и поиск
цен там, где ещё не искали (прогресс и «Остановить» те же). В api — методы `IPricingEngine` для поставщиков и контроллер
`api/specifications/suppliers` (404 ядра → `NotFoundException` → 404 `not_found`); во
фронте — окно «Поставщики» (кнопка в шапке и ссылка из вкладки «Себестоимость»): добавить,
обойти/остановить с опросом состояния раз в 3 с, загрузить прайс, примеры, удалить.

**Разделы.** У поставщика — список разделов КП (`Supplier.sections`), у предложения из
прайса — раздел файла (`SupplierOffer.section`); прайс по разделу заменяет только цены
этого раздела (`import_price_list(section=…)`), обход сайта раздел не ставит. При
сопоставлении позиция несёт свой раздел (`MatchRequestItem.section`), и предложение того
же раздела получает +0.05 — прайс нужного раздела чуть надёжнее выдачи. Текст запроса
поставщику (прайсы по разделам, срок действия цен, плановое изменение) генерируется на
фронте (`requestLetter`).

**Индексация к дате поставки** (`pricing/indexation.py`). Из прайса закупки считается рост
цен: у каждой позиции медианная цена по годам, отсюда изменения год к году (в коридоре
0.2–5, выбросы исключены), по группе 1С — медиана таких изменений; ставка группы — по
объединённым изменениям за последние три пары лет, не меньше десяти сравнений, иначе
общая по всем группам. `IndexationStore` хранит ставки, выбранные оператором
(`DATA_DIR/indexation.json`: раздел → % в год, источник history / supplier / official /
manual, примечание); `PUT /api/indexation` заменяет справочник целиком. Дата поставки —
у объекта во фронте, ставки — общие для компании; в выгрузку уходит `ExportRequest.indexation`
{дата, ставки, apply_to_kp}. Ядро: лист «Себестоимость» получает графы «Индексация, % в
год», «Цена на дату» (`=ROUND(O*(1+R/100)^лет,2)`, доля лет по дням) и «Стоимость на дату»
с итогом; при `apply_to_kp` базовая цена строки в приложениях №1.1/№1.2 индексируется
перед расчётом КП (`_indexed_item`). Фронт зеркалит формулу в `kp.ts`
(`indexedPrice`, `kpBase`), чтобы итоги и цены КП в интерфейсе совпадали с Excel; панель
«Индексация» подставляет ставки из истории по совпадению названия раздела с группой 1С
(точное, иначе общее начало, иначе общая ставка).

**Выгрузка `cost`** — книга «Себестоимость» (№, раздел, наименование, характеристики,
ед., кол-во, № поз. в ТХ, цена интернет + дата/источник, мин и макс по истории,
последняя закупка и дата, сопоставление (аналог — красным), выбранная цена и откуда,
стоимость `=F*O`, итог; «Дата / источник» у интернет-цены — гиперссылка на предложение),
«Покупки по истории» (по каждой сопоставленной позиции — покупки, на которых основан
эталон) и, если искали в интернете, «Предложения из интернета» (все найденные предложения
со ссылками, пометкой «аналог» и комментарием модели).
